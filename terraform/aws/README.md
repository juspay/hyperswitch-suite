# Hyperswitch Terraform Infrastructure

Modular Terraform infrastructure for Hyperswitch payment services - a complete AWS deployment with VPC, EKS, databases, proxies, and CDN.

## Self-hosting

The fastest way to self-host Hyperswitch on AWS: fork this repo and run
`scripts/self-host/generate.sh` from the repo root. It prompts for your
environment (account, VPC, domains, sizing) and renders a complete bundle —
a Terragrunt stack (`terraform/aws/catalog/stacks/standalone`) plus an ArgoCD
app-of-apps (`argocd/`) — with a step-by-step runbook (`SELF_HOST.md`).

## Module Layers

### Base Modules (`modules/base/`)
Atomic AWS resource wrappers - **never run Terraform here** (libraries only).

- `vpc/`, `subnet/`, `route-table/`, `network-acl/`, `vpc-endpoint/`
- `security-group/`, `security-group-rules/`
- `asg/`, `launch-template/`
- `alb/`, `alb-listener/`, `nlb/`, `nlb-listener/`, `target-group/`
- `iam-role/`, `s3-bucket/`, `dynamodb-table/`
- `lambda/`, `api-gateway/`

### Composition Modules (`modules/composition/`)
Service orchestration combining base modules - **never run Terraform here** (templates only).

| Module | Purpose |
|--------|---------|
| `vpc-network` | Complete VPC with multi-tier subnets, NAT, endpoints |
| `eks` | EKS cluster with managed node groups |
| `eks-kubernetes-resources` | K8s resources, cluster autoscaler, Helm deployments |
| `cloudfront` | CDN distributions with OAC, functions, policies |
| `database` | RDS Aurora PostgreSQL cluster |
| `elasticache` | ElastiCache Redis replication group |
| `envoy-proxy` | Ingress proxy with ALB + ASG |
| `squid-proxy` | Outbound HTTP/HTTPS proxy with NLB + ASG |
| `locker` | Card vault service with EC2 + NLB |
| `jump-host` | Bastion host for SSH access |
| `security-rules` | Cross-module security group rules |

### Application Resources (`modules/application-resources/`)
EKS application-level resources.

- `alb-controller` - AWS Load Balancer Controller
- `argocd` - GitOps continuous deployment
- `istio` - Service mesh
- `external-secrets-operator` - Secrets management
- `hyperswitch` - Application-specific resources
- `eks-iam` - IRSA configurations
- `shared-policy` - Shared IAM policies

## Deployment Guide

### Prerequisites

- Terragrunt >= 1.1
- Terraform >= 1.0
- AWS CLI configured with appropriate credentials
- kubectl (for EKS deployments)
- Helm 3.x (for Kubernetes deployments)

### Deployment Order

Units apply in dependency order, driven by each unit's `dependency` blocks
rather than a hand-written phase list — `terragrunt run-all apply` computes
it. The rough shape (see [`catalog/stacks/internal`](./catalog/stacks/internal/README.md)
for the exact phase table):

```
BOOTSTRAP (one-time: S3 + DynamoDB state backend)
   │
   ▼
Phase 1  vpc-network, route53, acm
   │
   ▼
Phase 2  database, elasticache, efs, kafka, locker
   │
   ▼
Phase 3  squid-proxy, envoy-proxy, jump-host
   │
   ▼
Phase 4  application-stack/eks-01
   │
   ▼
Phase 5  application-stack/{eks-resources, utils-load-balancer}
   │
   ▼
Phase 6  application-stack/apps/*  (alb-controller, external-secrets, istio,
         otel, vector-dr, loki, grafana, ratelimiter, hyperswitch,
         decision-engine, superposition)
   │
   ▼
Phase 7  security-rules  ⚠ deploy last — wires up cross-unit SG rules
```

### Step-by-Step Deployment

#### 1. Bootstrap State Backend

```bash
# Create S3 bucket and DynamoDB table for Terraform state
cd bootstrap/dev
terraform init
terraform apply

# Verify
aws s3 ls | grep hyperswitch-dev-terraform-state
```

#### 2. Fill in the environment's values

Edit [`live/terragrunt.stack.hcl`](./live/terragrunt.stack.hcl) — one `stack`
block per environment. Replace the `REPLACE_ME` placeholders (account ID,
AMI ids, IAM role ARNs, real domains) with real values; see the
[live layer README](./live/README.md) for the full list.

#### 3. Generate and commit the unit tree

```bash
cd live
terragrunt stack generate
git add . && git commit -m "regenerate dev/pre-prod/prod from the catalog"
```

This renders every unit from
[`catalog/stacks/internal`](./catalog/stacks/internal/README.md) into
`live/<env>/<region>/`. It only renders files — it does not evaluate unit
inputs, so a clean generate does not guarantee `plan`/`apply` will succeed.

#### 4. Apply

```bash
cd dev/eu-central-1
terragrunt run-all plan    # review first
terragrunt run-all apply   # units apply in dependency order; security-rules last

# Configure kubectl once eks-01 is up
aws eks update-kubeconfig --name <cluster-name> --region eu-central-1
```

Or apply a single unit and its dependencies:

```bash
cd dev/eu-central-1/database
terragrunt apply
```

## Environment Configuration

### Directory Structure

```
terraform/aws/
├── ARCHITECTURE.md          # This file
├── README.md                # Deployment guide
├── bootstrap/               # State backend infrastructure
│   ├── dev/
│   ├── integ/
│   ├── prod/
│   └── sandbox/
├── modules/
│   ├── base/                # Layer 1: Atomic AWS resources
│   ├── composition/         # Layer 2: Service compositions
│   ├── application-resources/  # Layer 3: EKS applications
│   └── cloudfront-resources/   # Layer 4: CloudFront shared
├── catalog/                 # Terragrunt units + stacks (the source of truth)
│   ├── units/                    # one terragrunt.hcl per composition module
│   └── stacks/
│       ├── internal/             # dev / pre-prod / prod (creates its own VPC)
│       └── standalone/           # self-host, BYO-VPC
└── live/                    # Generated + committed — do not hand-edit
    ├── terragrunt.stack.hcl      # the only file to edit here
    ├── dev/eu-central-1/
    ├── pre-prod/eu-central-1/
    └── prod/eu-central-1/
```

### Environment Values

There is no per-component `terraform.tfvars` anymore. All environment
differences (sizing, domains, AMIs, account IDs) live in one place —
the `values` block of each `stack` in [`live/terragrunt.stack.hcl`](./live/terragrunt.stack.hcl).
See [`catalog/stacks/internal/README.md`](./catalog/stacks/internal/README.md)
for which values are required vs. optional per unit.

### Remote State

Every unit's backend is generated by `catalog/stacks/internal/root.hcl`
(`remote_state` block); units reference each other's state via Terragrunt
`dependency` blocks, not raw `terraform_remote_state` data sources:

```hcl
dependency "vpc" {
  config_path = "../vpc-network"
}

# Use outputs
vpc_id = dependency.vpc.outputs.vpc_id
```

State key layout: `s3://<state_bucket>/<env>/<region>/<unit-path>/terraform.tfstate`.

## Common Operations

### Update Squid Egress Allowlist

```bash
# Edit the per-environment allowlist (outside live/, read directly by the unit)
echo ".example.com" >> ../../whitelisted-domains/dev-allowedlist.txt

cd live/dev/eu-central-1/squid-proxy
terragrunt apply   # triggers an instance refresh
```

### Scale an EKS Node Group

Edit the relevant `values` in [`live/terragrunt.stack.hcl`](./live/terragrunt.stack.hcl)
(e.g. `generic_compute_desired_size`), then:

```bash
cd live
terragrunt stack generate
cd dev/eu-central-1/application-stack/eks-01
terragrunt apply
```

### View Unit Outputs

```bash
cd live/dev/eu-central-1/application-stack/eks-01
terragrunt output

# Specific output
terragrunt output -raw cluster_endpoint
```

## Troubleshooting

### State Locked

```bash
# Find lock ID in error message
terragrunt force-unlock <lock-id>
```

### Instance Unhealthy (ASG)

1. Check CloudWatch logs
2. Verify security group rules
3. Check S3 config bucket access
4. Verify IAM role permissions

### EKS Node Not Ready

1. Check node security group
2. Verify VPC endpoints (ECR, S3, SSM)
3. Check IAM role for node group
4. Review CloudWatch Container Insights

### Database Connection Issues

1. Verify security group allows traffic from source
2. Check subnet group configuration
3. Verify VPC routing (NAT for outbound)

### Envoy Ingress Issues

1. Verify the envoy-proxy ALB target group is healthy
2. Check the ACM certificate status feeding `envoy-proxy`'s HTTPS listener
3. Verify security group rules from `security-rules`
